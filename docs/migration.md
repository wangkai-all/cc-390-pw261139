# 迁移方案：双写与日志重放如何不偏离，差异如何定位到原批次

## 数据模型

宽表记录（嵌套 JSON）拆为三类表，**拆分是结构归一化，不是改字段名**：

| 表 | 内容 | 关键不变量 |
|---|---|---|
| `masters` | 非数组顶层字段（标量/对象）原样保留 | 嵌套对象不展开，避免语义丢失 |
| `sub_item_groups` | 每个数组字段一行 `(field, count)` | **空数组** `count=0` 有行，与"字段缺失"（无行）区分 |
| `sub_items` | 每个数组元素一行 `(field, seq, item)` | **顺序**由 `seq` 保留；**重复项**各占一行，不去重 |
| `revisions` | 每次改版一行 `(version, batch_id, checksum)` | 历史修订可追溯，校验和来自接入时刻 |

重组 `assemble` 是拆分 `split` 的严格逆运算（`app/core.py`，13 项单元测试固定该性质），
兼容查询服务靠它对旧接口返回逐字节等价的结果。

## 两条迁移路径为什么不偏离

双写与日志重放可能产生两套结果，靠以下五条保证它们必然收敛到同一份字节：

1. **日志先行（WAL）**：转换器收到批次后，先向 `ingest_log.jsonl` 追加并 `fsync`，
   再写任何存储。此后无论哪侧失败，恢复所需的一切都在日志里。
2. **版本号在接入时分配并写入日志**：版本由旧系统（迁移期的排序事实源）给出 `latest+1`，
   落进日志行。重放不是"重新解释输入"，而是按日志里已确定的 `(record_id, version, payload)`
   原样应用——双写与重放的输入逐字节相同。
3. **同一个拆分纯函数**：双写（`/apply`）与重放（`/replay`）都调用 `core.split`，
   无随机、无时钟、无外部状态，同输入必同输出。
4. **幂等应用**：按 `(record_id, version)` 先删后插，批次注册表 `INSERT OR REPLACE`；
   重放跳过已应用批次，重复执行无副作用（e2e 验证二次重放零新增）。
5. **失败不混态**：旧宽表写失败 → 整批失败（日志已留底，可安全重试）；
   新版存储写失败 → 批次标记 `pending_replay`，绝不出现"写了一半"的中间态。

## 对账：怎么发现偏离

全量对账（网页「新旧查询对比」页，或 `GET /api/reconcile`）对每个 `(记录, 版本)` 做三方校验：

```
stored_checksum   revisions 表在接入时写入的校验和（日志批次的确定性产物）
legacy_checksum   旧宽表现存内容实时算的校验和
new_checksum      兼容服务从三类表重组后实时算的校验和
```

- 三者一致 → `ok`；
- `legacy ≠ stored` → 旧侧被绕过管道改动（双写漏网之鱼）；
- `new ≠ stored` → 新版存储与日志不一致（重放遗漏或应用错误）；
- 内容不一致时附**逐路径差异**（如 `$.hourly[2].pv: 旧=10, 新=12`、`$.top_pages: 旧=[], 新缺失`），
  数组按序对比，能区分"顺序错了"和"值错了"。

## 差异定位到原批次

每条修订、每行宽表都带 `batch_id`；批次号即日志行号（`b000123` ↔ 第 123 行）：

1. 对账报告按批次聚合，直接给出坏批次号；
2. `GET /api/batch_source?batch_id=...`（网页点批次号）取回该批次的**原始输入**，
   含接入时分配的版本号与时间戳；
3. 修复手段就是把该日志行重新 `/apply` 一次——幂等，且与首次应用逐字节一致。

## 晚恢复演练（兼容链路落后于真相源）

- **新版存储故障**：故障期双写部分失败，批次进入待重放（`/pending` 是带外运维通道，
  故障期仍可观察积压，类比消费者滞后监控）。恢复后 `/replay` 按日志顺序追平，
  对账转绿前下游不应切流。
- **兼容服务故障**：查询侧 503，旧接口不受影响（双写仍在推进）。恢复后兼容服务
  直接读已追平的三类表，对同一输入版本返回等价结果。
- **切流判据**：连续对账全绿（三方校验和一致）后，下游把 `/api/v1/report` 的地址
  从旧系统切到兼容服务即可，契约不变。

## 已知限制（演示边界）

- 拆分只归一化顶层数组字段；子项内部的嵌套数组原样保留在子项 JSON 里（语义不丢，但不可按内层字段索引）。
- 版本号分配依赖旧系统在线；旧系统不可用时接入失败（日志未写，可安全重试）。
- 接入日志是本地文件；生产对应物是 Kafka/WAL 这类可复制日志，语义相同。
- 对账是全量逐版本比对，演示规模足够；生产应改为按批次校验和抽样 + 变更数据捕获增量对账。
